# Ken LLM gateway

Private localhost service using the official `codex app-server` stdio protocol and existing **ChatGPT login**. It does not extract cookies/tokens or call undocumented ChatGPT web endpoints. The account must have Codex access; requests consume Codex plan limits. This is a local prototype, not a public inference API.

```text
Android → backend Java → codex-chatgpt provider → localhost gateway → Codex → model
                      → openai / ollama / existing providers
```

## Run

Python 3.11+ and `aiohttp` are required (`requirements.txt`). Log in once with `codex login` on the machine running the gateway. `codex login status` must show ChatGPT. The current development CLI is the bundled desktop binary; override `KEN_CODEX_CLI` when installing elsewhere.

From the project root:

```sh
python services/llm-gateway/local.py start
python services/llm-gateway/local.py models
python services/llm-gateway/local.py smoke
python services/llm-gateway/local.py configure-backend
python services/llm-gateway/local.py status
python services/llm-gateway/local.py stop
```

`configure-backend` writes only the dedicated, owned `robotai_ken` schema. It creates one tagged config and preserves existing defaults if present. It refreshes this gateway's token/URL on rerun. Restart the Java services after using it to clear cached configuration. No database migration is needed: it uses the existing provider field/factory.

The local manager creates `.local/llm-gateway.json` (permissions 0600), containing a random **internal gateway token**, not an OpenAI API key. It is used as `sys_config.apiKey` solely to authenticate Java → gateway. Never share or commit this file. Runtime stderr/access logs contain no prompts or auth tokens. Log: `.local/llm-gateway.log`.

## Backend configuration

| Field | Value |
|---|---|
| provider | `codex-chatgpt` |
| apiUrl | `http://127.0.0.1:8787/v1` |
| apiKey | Internal gateway token generated by the local manager |
| configName | `codex-default`, or a model returned by `/v1/models` |
| modelType | `chat` or `vision` |
| enableThinking | false → `low`; true → `medium` |
| contextLength | 4096 suggested for short conversations |

The management UI now lists this provider. `codex-default` selects the account's default available model; unavailable explicit names return 400, never silently change models. OpenAI-compatible and Ollama providers retain their original settings and credentials. Role `modelId` chooses a config; a null role model uses the existing default-selection mechanism.

This adapter supports text and **one inline JPEG/PNG image** per request. Java removes runtime tool callbacks/context for this provider. Gateway rejects tool messages, tools, external image URLs, JSON response formats and embeddings. Select another provider for function calling or embeddings. `temperature`, `top_p`, `max_tokens` / `max_completion_tokens`, `stream_options` are accepted for Spring AI compatibility but are not mapped to Codex; generated output is bounded by the turn timeout, not by an exact token cap. Gateway accepts reasoning effort supported by the selected model. Request timeout is 90 seconds by default.

## HTTP contract

All endpoints require `Authorization: Bearer <internal-token>`:

- `GET /health`: process health, busy flag and resident session count (does not validate login).
- `POST /v1/sessions`: backend-generated UUID `session_id`, authenticated `owner_id`, model/effort and initial `messages`. Opens a private process/thread and completes an internal warmup turn before returning `state=ready`.
- `POST /v1/sessions/{id}/heartbeat`: renew the resident session lease.
- `DELETE /v1/sessions/{id}`: idempotently interrupt/close that connection and remove its private directory.
- `GET /v1/models`: checks login and returns current available models.
- `POST /v1/chat/completions`: text `messages`, or user content parts containing text and an inline `image_url` data URL, `model`, `stream`, optional `reasoning_effort`. `/chat/completions` is an alias.
- Streaming: OpenAI-compatible SSE `choices[].delta.content`, final `finish_reason=stop`, then `[DONE]`. Stream failure sends an `error` event without successful `[DONE]`; HTTP status cannot change after headers were sent.
- Turn HTTP disconnect: interrupt and drain a resident turn; the next turn rebuilds context from backend history. Disposable probes terminate their process. Session deletion, lease expiry and gateway shutdown terminate resident processes. A remote interrupt is best effort; there is no guarantee it reverses already consumed quota.
- Default limits are 16 resident connections and 4 active turns/warmups. Different users run concurrently, with one active turn per connection. Capacity overflow returns 429. Set `KEN_LLM_MAX_SESSIONS`, `KEN_LLM_MAX_ACTIVE`, `KEN_LLM_SESSION_LEASE` (120 seconds) and `KEN_LLM_TIMEOUT` (90 seconds) for the host/account capacity. Java renews leases every 30 seconds. Invalid payload/model returns 400, auth 401, upstream/login/timeout before streaming 503.

Limits: 100 messages / 32000 text characters / 3 MiB body / one image of at most 2 MB. Images are written with mode 0600 in a private request directory, supplied as Codex `localImage` input, and deleted on success, failure, timeout or disconnect. No remote URL fetching or user-supplied filesystem paths. Backend owns history and trims it before calling. Resident conversation requests carry `X-Ken-Session-Id`, supplied only by the authenticated Java backend. Each connection retains one ephemeral thread and private cwd/process; probes without that header remain disposable. Only newly appended messages enter the thread. Changed system instructions, compacted/deleted history, switched speakers or interrupted output rebuild the thread from authoritative backend history. Recognized robot metadata tags are normalized to match persisted Java replies. Retrieved personal facts are included as transient context and invalidate the thread when changed/removed. No automatic LLM retries or provider fallback.

## Isolation and limitations

The gateway disables each configured MCP transport (`enabled=false`, verified via `config/read`), plugins/apps/hooks/shell/unified execution/browser/computer use/subagents and other capability flags. Each thread and turn sets `environments=[]`, no workspace/capability roots, no dynamic tools, read-only sandbox, and never approvals. Any server tool request is denied; non-chat items abort the turn. Existing global login remains managed by the official CLI; its normal auth refresh/state writes may still occur.

Validated with bundled Codex **0.162.0-alpha.17.2**. Empty environments are experimental protocol fields: an incompatible CLI must fail rather than silently enable capabilities. Verify the isolation tests and model catalog after updates. Bind is deliberately `127.0.0.1`: Java and gateway must run on the same host; this version does not expose an unauthenticated LAN service or provide a multi-user account pool.

The authenticated app opens its WebSocket after login. Server sends `session/preparing`, then `hello` with `ready=true` after warmup succeeds; failure sends `session/failed` and closes the connection. Frontends wait for readiness rather than TCP/WebSocket open. App screen changes and local sleep suspend audio while retaining the foreground connection; explicit disconnect, logout and backgrounding end it. Authenticated app sessions do not use the role's conversational inactivity timeout. Legacy device inactivity settings remain in effect.

On disconnect, Java stops synthesis/playback, commits any interrupted turn, waits up to `conversation.summary-close-timeout-seconds` (60 by default) for final summary persistence, then deletes the gateway session and clears memory. Original messages are already stored independently. On summary/database failure or timeout, cleanup still closes the connection; persisted message history remains recoverable and a warning is logged. A missing heartbeat eventually releases connections left by a crashed Java process. Graceful backend shutdown waits for pending cleanup.

Gateway-only CLI overrides set `skills.max_context_tokens=1`; the user's Codex app skill configuration is unchanged. The Codex conversation's token estimate reserves 512 rather than 4000 tool tokens because robot tools are removed, preventing a 4096-context configuration from compacting/replacing the thread after every short turn.

Live sample on 2026-10-12: two users warmup **4.7 / 7.3 s**, then first-text latency **2.0–2.4 s**, followup **2.15 s** with the same thread. Private processes/threads remained distinct and were removed after close. These are sample measurements, not a latency guarantee. Warmup consumes a short Codex turn; final summaries also consume model usage. No Fast mode or model change is enabled automatically.

## Tests

```sh
PYTHONPATH=services/llm-gateway python -m unittest discover -s services/llm-gateway/tests -v
```

Java adapter tests: `CodexChatGptModelProviderTest`. `KEN_LLM_LIVE=1` enables its opt-in real gateway test (consumes a Codex turn); otherwise it uses a fake SSE HTTP service.
